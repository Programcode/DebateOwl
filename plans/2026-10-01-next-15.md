## Security and data protection

### 1. Confirm the leaked provider keys were rotated

OpenAI, Anthropic and Jina keys were committed to git history at the start of the project. History was scrubbed on 2026-08-20, but scrubbing does not revoke a key. At that time the Supabase secrets still showed `updated_at` 2026-01-29, the day the project was created.

- Adam: rotate the keys in each provider dashboard, or confirm they were already rotated. Confirm the Google key too.
- Then set the new values on production and staging with `supabase secrets set`. This needs Adam's authorization.
- Done when `supabase secrets list` shows a fresh `updated_at` for every provider key on both projects. Record only the date, never the value.

If every model call now goes through OpenRouter, delete the unused direct-provider secrets instead of rotating them.

### 2. Limit promo-code guessing

`supabase/functions/redeem-promo/index.ts` has no attempt counter. `public.redeem_promo_code_atomic(text)` is granted to `authenticated`, so any signed-in user, including a demo-code user, can call it directly through PostgREST and skip the Edge Function. The limit therefore has to live in SQL.

- Add a per-user failed-attempt window inside `redeem_promo_code_atomic`, modelled on `demo_access_attempts`.
- Return the same error for an unknown code and for a locked-out user.
- Prove it with a pgTAP test: N failures lock the user, success resets the count, and another user is unaffected.

### 3. Account deletion and data export (shipped: #83)

There is no `auth.admin.deleteUser` path and no export. Settings only clears local session data. Most users are school students in the EU, so they need both.

- Add one Edge Function with two actions: export everything the user owns as JSON, and delete the account. Deletion cascades through debates, sources, source files in storage, results and usage rows, then deletes the auth user.
- Cancel any Stripe subscription before deleting, or refuse to delete while one is active. Pick one and document it.
- Settings gets a "Download my data" button and a "Delete account" button that asks the user to type a confirmation.
- Prove it with a pgTAP or full-stack test: after deletion, no row in any public table references the user id. Also prove one user cannot export or delete another.
- Update `src/pages/PrivacyPage.tsx` if it promises anything different.

### 4. Tighten the Content Security Policy

`vercel.json` `connect-src` still allows `api.openai.com`, `api.anthropic.com`, `generativelanguage.googleapis.com`, `r.jina.ai`, `s.jina.ai` and the wildcard `*.supabase.co`. The browser has not called any provider directly since AI moved server-side.

- Remove the provider hosts. Remove `*.supabase.co` once staging and preview origins are listed explicitly; keep the production project host.
- Check Google Docs export (`oauth2.googleapis.com`, `www.googleapis.com`) before removing those.
- Add `form-action 'self'`. Drop `X-Frame-Options: SAMEORIGIN`, which contradicts `frame-ancestors 'none'`.
- Prove it with the Chromium E2E suite plus a manual prod-preview check that the browser console shows no CSP violations on every route.

### 5. pgTAP coverage for untested tables (shipped: #80)

These tables have RLS enabled but nothing in `supabase/tests/` asserts their policies: `shared_items`, `user_roles`, `admin_grants`, `api_keys`, `source_files`, `rate_limits`, `global_prompts`, `webhook_events`, `user_data_clear_markers`.

- Start with `user_roles` (a user must not be able to grant themselves admin) and `shared_items` (public read only through the share code, owner-only write).
- For the deny-all tables, assert that `authenticated` and `anon` see zero rows and cannot write.
- Run through `./.superset/db-gate.sh`.

## Operational safety

### 6. A read-only backend drift check (shipped: #79)

Vercel ships the frontend on merge, while migrations and Edge Functions are deployed by hand. That gap has already caused drift: on 2026-09-30 production lacked two migrations and ran pre-#75 functions. Nothing in the repo detects it.

- Add `npm run backend:status`. It runs `supabase migration list --linked` and `supabase functions list`, compares them with `supabase/migrations/` and the function folders on the current commit, and prints what is pending. It must be read-only.
- Optionally add a step to `prod-canary.yml` that fails when production is missing a migration that `main` has. That check would need a read-only token, which is Adam's call.
- Document it in `docs/operations.md` as the first step of every backend deploy.

### 7. Alerts that reach Adam

The production canary runs daily, but a failure only shows in GitHub. Edge Functions log only to `console`, so backend errors never reach Sentry.

- Route `prod-canary.yml` failures to a channel Adam reads.
- Add Sentry for the Deno Edge Functions through a small shared wrapper in `_shared/`, with the same scrubbing rules as `src/lib/observability.ts`. Start with `ai`, `ai-stream` and `stripe-webhook`.
- Alert on repeated `stripe-webhook` failures, since a missed webhook means a paying user without access.

### 8. Make staging usable (shipped: #81)

`staging-e2e.yml` is skipped unless `STAGING_E2E_ENABLED=true`, and a skipped job is not a pass. Staging has no migration or function sync procedure, and the admin staging switcher from the backlog was never built.

- Write the staging sync procedure, reusing `backend:status` from item 6 against the staging ref.
- Build the admin-only switcher that sets the `debate-supabase-env` localStorage key that `src/lib/supabase/env.ts` already reads.
- Then enable the staging workflow. Applying anything to staging needs Adam's authorization.
